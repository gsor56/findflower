System Guide & Troubleshooting

How FindFlower handles scanning, server states, local data, and routing.

Read this when something looks wrong and you want to know whether the problem is your connection, your browser, or the server. Every number on this page is the number the code actually uses, so if the site behaves differently from what is written here, the page is out of date and worth reporting.

It does not explain the model. How it works covers that, and Privacy covers what happens to a photo once you send it.

The status dot

Above the upload frame on the scan page sits a small dot with a label beside it. It reports one thing: whether the machine that runs the model answered a health check. The page asks once when it loads, and stops waiting after 8 seconds.

Checking scanner…
The state the page opens in, while the health check is still out. On a normal connection it lasts well under a second.
Ready to identify
The check came back in under 1.5 seconds, so the model is already running. Expect a result a second or two after you send a photo.
Waking up the model…
Either the check took longer than 1.5 seconds, or it answered with a server error. The host suspends the model when nobody has used it for a while, so the first scan after a quiet spell has to start it up again. Send your photo anyway. It will go through, it just takes longer.
Scanner offline
Nothing came back at all. Most of the time that is the connection at your end. If your connection is fine the service is probably restarting, so wait a few minutes and reload. Everything you have already identified is held in this browser and stays readable in the meantime.

Why a scan sometimes takes a minute

A model that is already running answers in about a second. One that has been suspended has to load its weights first, and that is the wait people notice. Rather than leave you watching a spinner, the page rewrites its own message on a fixed schedule, so you can tell slow apart from stuck.

Straight away
The photo has gone and the page says it is analysing.
At 6 seconds
Longer than a warm request should take, so the wording changes to warn you that a first try can be slow.
At 20 seconds
By now it is clearly a cold start, and it says so plainly instead of pretending otherwise.
At 45 seconds
Slower than a cold start normally runs, but still worth waiting out.
At 95 seconds
The request is cancelled and you get an error.

If it does time out, try once more before deciding it is broken. The attempt that failed usually leaves the model running, which makes the second one quick.

Your photo reaches the model through a small proxy rather than going straight to the host, so a request can be held up in the middle without either end being down. The API reference has the endpoint and the response shape if you would rather call it yourself.

What an account does

This is the part people most often expect to work differently than it does, so it is worth being blunt about.

Do I need an account to identify a flower?
No. The scanner works signed out, and a scan you make as a guest is saved exactly the way a signed-in one is.
Then what does signing in change?
It keeps records apart. Scans made while you are signed in are filed under your account, so if somebody else uses the same browser their history and yours do not run together. Auth0 handles the sign-in itself, which is why FindFlower never sees your password. It also gets you a handle to post with in the community.
Will my history follow me to another device?
No, and this is the one to remember. Your scans, thumbnails, streak and badges are written to this browser and nowhere else. Signing in somewhere else gives you the same account with an empty history, because there is no copy on a server to pull down. The sign-in page says as much before you commit to it.
Can I get my data out?
Yes. Your dashboard will write the whole lot to a JSON file in your downloads. Treat it as a copy to keep or to read yourself. There is no import to match it, so it will not refill another browser for you.

Where each thing is kept

Two places hold data, and nearly every question about a missing record comes down to which of them you are looking at.

Scans, thumbnails
A browser database named findflower, on this machine. Photos are shrunk to 320 pixels on the long edge before they are stored, so a long history stays small. Streaks and species counts are added up from those rows whenever a page needs them, which is why deleting a scan changes the numbers straight away.
Unsent feedback
Local storage in this browser, until you decide to send it. Nothing goes anywhere on its own.
Community post text
The FindFlower server. This is the one thing here that leaves your machine on purpose, and it has to, or nobody else could read what you wrote. For the same reason it is the one thing that does follow you to another device.
Photos on a post
Not uploaded. A post carries its text; the identification behind it and its thumbnail stay local.

So clearing your site data, or opening FindFlower in a different browser, a different profile, or a private window, empties the local half of that list. Posts you have already published are unaffected and load as usual, because they were never sitting here to begin with.

If a post will not send, it is nearly always one of two things: you are signed out, or you have not claimed a handle yet. The community server sleeps when it is idle too, so the first load of the feed after a quiet spell can sit empty for a moment before anything shows up. The community page goes into its own storage in more detail.

Links, 404s and page changes

FindFlower is a set of static files. A path like /pricing is served from pricing.html, and both spellings of the address reach the same page. When there is no file behind a path you get the not-found page, which has a working search on it. A mistyped address, or a link from an older version of the site, is almost always the cause.

Not every dead end is a 404, though, and the difference tells you where to look.

A species page that shows almost nothing
Species profiles are filled in from Wikipedia and Wikidata as you open them rather than being baked into the page. If a name cannot be matched there, the profile still loads with whatever is available and offers you a Wikipedia search instead. Sparse, but not an error.
An article link that says there is no entry
Written entries are looked up by an id in the address. An id that no longer exists gets you that message on the article page rather than a 404, with a link back to everything that has been published.
A scan that has gone from your history
Check you are in the same browser, and the same profile, that made it. Scans are never fetched from anywhere, so one that is missing means the local database is not the one you have in mind.

Moving between pages does not usually reload the browser. A link is caught in the page, the next document is fetched, and its main content replaces what was there, with the title and the address updated to match. If any step of that fails the site stops being clever and performs an ordinary full load of the same URL, so a failure costs you a slower page change rather than a blank screen. Two pages always load in full: the scanner, which is holding a live camera stream, and sign-in, which has to catch a redirect back from Auth0. Neither one survives being swapped in halfway.

Working without a connection

You cannot use FindFlower offline. Nothing is cached for it.

Loading or reloading any page needs the network, and a new scan needs it twice over, since the model runs on a server rather than in your browser. It is better to say that here than to let you find out halfway up a hillside with no signal.

Your saved history is not lost while you are offline. It is sitting in the browser database and reads back normally as soon as a page can load again.
