Architecture and dataset

How the model is trained, and how a prediction is scored.

Revised 20 August 2026
Beta 0.9.8

There are two halves to this, built and measured separately: a dataset assembled from open-licensed field observations, and a classifier that runs on a server rather than on your device. Both are described as they stand today, including the parts that are not finished. Every figure was read out of the repository it describes.

The short version: 1,500 flowering species were chosen by how often people actually photograph them, each one is being filled to exactly 100 checked images, and the classifier that answers a scan today still knows 116 of them. The gap between those two numbers is the honest state of the project.

The target list

The class list is not botanical judgement. It comes from iNaturalist’s species-counts endpoint, restricted to flowering plants (Angiospermae, taxon 47125, inside kingdom Plantae, 47126) and ordered by observation count, descending. 5,458 valid species came back, and the first 1,500 became the target.

Ordering by observation count is a bias, and worth naming as one. It picks the species people meet, not the species that matter botanically. A rare orchid two valleys over is absent by construction, and coverage follows wherever amateur naturalists photograph, which is heavily Europe and North America. What the ordering buys is the one thing that makes the rest possible: for a common species, 100 usable photographs exist.

The list is frozen in a manifest, version 5, generated 16 August 2026, so that a worker starting tomorrow and a worker that started last week are filling the same 1,500 slots in the same order.

One hundred images per class, no exceptions

Every class gets exactly 100 images. Not a minimum and not an average, a count, enforced when the folder is written. The reason is class imbalance: if a common daisy arrives with 400 photographs and its neighbour with 30, a classifier learns the prior rather than the plant, and its confidence turns into a report on the dataset instead of the flower. Fixing the count removes the question instead of correcting for it later.

Up to 250 raw candidates are fetched per class, 200 observations to a page, with licences restricted to CC0, CC BY and CC BY-NC. Roughly three in five of those are thrown away. Each image has to clear every check below, in the order they run, and then the folder is audited as a whole.

The first six are cheap arithmetic on the decoded pixels, and they remove the failure that dominates citizen-science archives: photographs of nothing in particular. A hand over the lens, a lawn, a white sky, a screenshot of a field guide. None of those need a model to reject.

The seventh is a perceptual hash. Observations often carry the same flower photographed twice a second apart, and near-duplicates inflate a class without adding anything to learn from. Worse, they leak between the training and validation splits and quietly flatter the accuracy figure. Any candidate within a Hamming distance of 6 of an image already kept is dropped.

The eighth is the only learned step. Every surviving image is embedded with mobilenetv3_small_100.lamb_in1k, a class centroid is computed, and images whose cosine similarity to that centroid falls below 0.30, or more than three median absolute deviations below the class median, are rejected as outliers. This is the step that catches the mislabelled observation and the photograph of the whole hillside.

A final pass runs a larger MaxViT classifier over the folder and flags an image only when the evidence is unambiguous: another class predicted above 0.92 confidence, a margin over the expected class above 0.25, and the expected class itself scoring under 0.10. Those three conditions together are a deliberately narrow net. A weaker rule would let the audit model overwrite the taxonomy with its own opinion, which is the wrong direction of trust.

A class folder is written only when it holds exactly 100 survivors. Fewer than that and the class is not published at all. It goes back on the queue instead of shipping thin, which is the whole reason the collected count climbs slowly.

Five CPUs that don’t talk to each other

Fetching, decoding and filtering 250 candidates for 1,500 classes does not fit in one session. The work runs as five Kaggle CPU notebooks, each given the same script and a different shard index. A class belongs to a worker when its position in the frequency-ranked manifest, minus one, is congruent to that worker’s index modulo five. Worker 0 takes classes 1, 6, 11; worker 1 takes 2, 7, 12; and so on.

Interleaving rather than splitting into contiguous blocks matters more than it looks. The manifest is sorted by observation count, so a contiguous split would hand worker 0 every abundant, easily-filled species and worker 4 nothing but rarities that fail the 100 floor. Round-robin gives all five the same mix of easy and hard, and their throughput stays comparable.

There is no coordinator. Each worker writes progress/shard-XX-of-05.json to the dataset repository as it finishes classes, and reads the other four files when it starts so it can skip anything already done. Progress is a set of files in the artifact store rather than a service, which means a worker dying costs one class in flight and nothing else. Each run stops at 10 hours 45 minutes, inside Kaggle’s session ceiling, so it always exits by finishing an upload rather than by being killed mid-write.

The 1,500-class manifest travels inside the notebook rather than beside it: gzipped, base64-encoded and substituted into the script as a literal. A notebook that carries its own input has no attach step to get wrong and no path to break when it is cloned for the sixth time.

One pass has no counterpart in the original design. Sessions that uploaded a folder and then died before writing progress left classes that were complete in the repository but unrecorded, and the next worker would have refetched all 250 candidates for them. A recovery step now lists the remote repository, counts images per folder, and marks any folder holding 100 or more as complete with the marker remote-folder-recovery in place of a timestamp. It is bookkeeping, not curation, and the marker is there so the two can never be confused later.

831 and 669 add to 1,500, which is the only arithmetic on this page that has to hold. The last row is the one worth explaining. An earlier version of the target list was drawn from Plantae as a whole rather than from flowering plants, and it produced 172 class folders of ferns, conifers and mosses that are complete, correctly filtered, and not part of this dataset. They still sit in the repository because deleting them is a destructive operation on the only copy. Counting them would give 1,003 classes and 104,720 images, and that number is wrong in a way that is easy to miss, so it is not quoted anywhere.

The 60 classes carrying 148 to 200 images are the same kind of residue and the same kind of honesty problem. They were filled before the exactly-100 rule existed. Left alone they are the largest classes in the set by roughly two to one, which is precisely the imbalance the floor was introduced to prevent. They will be trimmed to 100 before training rather than kept as a bonus.

The inference engine

The served model is a Vision Transformer. An image arrives, is rescaled to the unit interval, resized bilinearly to 224 × 224, normalised with a mean and standard deviation of 0.5 on every channel, and passed through a single ONNX Runtime session on the CPU execution provider. The logits go through a softmax and the top five come back with their probabilities.

It runs on a server, and the first version did not. Running the network in the browser is attractive on paper, since the photograph never leaves the phone, and it fails on the two things that actually matter on a phone. A transformer this size is a multi-hundred-megabyte download before the first identification, over a connection that is frequently a field with one bar. And the arithmetic runs on the handset, so the battery pays for it, and a mid-range Android takes long enough that people assume the page has hung. Server-side, the phone uploads one JPEG and holds a request open.

Being straightforward about the trade: this means your photograph is sent to a server to be classified. It is held only for the moment it takes to run the model, it is not stored, and it is not attached to an account. What is kept about a scan, the prediction, the confidence and the image itself, lives in your own browser’s IndexedDB and is never uploaded. The guide lists what sits where if you want the short version. In-browser inference would have been the stronger privacy claim, and it is not the one being made.

Why the weights are fp32

The host has 512 MB of memory, which turns the obvious optimisation upside down. Half-precision weights make a 165 MB file and a 228 MB resident process, and a 511 MB peak while loading, because the runtime converts fp16 to fp32 to execute on CPU and briefly holds both. That is one megabyte of headroom. Full-precision weights make a 329 MB file, a 389 MB resident process, and a 409 MB peak. The larger file is the one that fits.

The weights are also stored beside the graph as external data rather than inside a single protobuf. Loading one self-contained file peaked at roughly 670 MB, about twice the file size, since the parser holds the serialised copy and the deserialised tensors at once. Memory-mapping the tensors from a separate file peaked at roughly 395 MB instead. Top-1 and top-5 outputs were checked as identical across all four combinations before any of this was deployed.

What this does not do yet

The model in production recognises 116 species. The dataset above targets 1,500. Those are two separate things, and nothing has been trained on the new one. Its manifest records zero epochs and no validation accuracy, which is accurate. Collection has to finish first.

No accuracy figure is published for the 116-class model either. One will be, measured on a held-out split, once there is a split worth quoting. A number without a stated test set is decoration.

The ranking bias described at the top is a limitation as much as a design choice. A rare endemic that six people have ever recorded is absent and will stay absent, because there is no way to reach 100 filtered images of it. A taxonomically balanced list would produce a model that fails on the flower in front of you and succeeds on the one you will never see.

Three known defects, stated plainly: 60 collected classes are still over-filled and will be trimmed; 172 folders from a superseded list are still in the repository and need removing; and the dataset repository is private while the licence attribution per image is assembled, so it cannot yet be linked from Data & integrations.

Where the numbers come from

The iNaturalist API, /v1/observations/species_counts and /v1/observations, filtered to Angiospermae (taxon 47125) within Plantae (47126), research-grade records, open licences only.

Target manifest version 5, generated 16 August 2026 from 5,458 valid species and frozen since. The embedding model for outlier rejection is mobilenetv3_small_100.lamb_in1k, and the label audit uses MaxViT.

Memory figures were measured on the deployment host, the 512 MB tier, using the ONNX Runtime CPU execution provider.

Photographs on iNaturalist are the work of the observers who took them and remain under the licences they chose. FindFlower filters and counts them. It does not own them.
